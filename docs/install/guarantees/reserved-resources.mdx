title: "Reserved Resources"
description: "The hard bounds each execution runs under: a sandbox memory cap, a per-operation timeout, and a per-box process lifetime"
icon: "memory"
---

Every execution runs in its own sandboxed engine child process, and those processes are bounded by the sandbox's own resource limits rather than by a dedicated container. One execution's memory blow-up takes down its own operation, not its neighbours: a box that hits a limit is torn down and rebuilt, and the next execution starts on a clean process.

<Note>
This is one of the Inboxfm Connect execution guarantees for self-hosted deployments. For the full scope of what does and does not survive a crash, see [Crash Recovery](./crash-recovery).
</Note>

Two promises follow from one mechanism:

## An OOM kills one execution, not its neighbours

The engine child process is forked with a Node heap cap (`--max-old-space-size`) derived from `AP_SANDBOX_MEMORY_LIMIT`. A piece that exhausts the limit fails its own operation with a sandbox memory error; that sandbox is invalidated and rebuilt, and no other in-flight execution is touched. In `SANDBOX_CODE_ONLY`, Code steps are additionally bounded inside their own 128 MB V8 isolate (see [Sandboxing](../architecture/sandboxing)).

## A hang is bounded in time

Each operation is capped at 60 seconds (a code constant on both execution paths — not a configurable knob), and the engine child process itself is bounded by `AP_FLOW_TIMEOUT_SECONDS`. An execution that exceeds either fails with a sandbox timeout error rather than wedging a box forever. Combined with the per-box one-operation-at-a-time rule, this is what keeps a slow piece from starving the pool.

## What this is not

These are **process-level limits inside the app container**, not orchestrator-enforced per-execution containers. All sandboxes share the app pod's CPU and memory budget, so:

- The app container's own resource requests/limits are the real capacity planning unit — a pod starved of CPU slows every execution it hosts. Size it for your peak concurrent executions, and scale by adding replicas ([Autoscaling](../architecture/autoscaling)).
- Noisy-neighbour protection between projects is admission control (per-project concurrency caps), not a reserved CPU slice.

## Governing configuration

| Variable | Default | Effect |
|---|---|---|
| `AP_SANDBOX_MEMORY_LIMIT` | `1048576` (KB = 1 GB) | The engine child process's Node heap cap |
| `AP_FLOW_TIMEOUT_SECONDS` | `600` | The engine child process's lifetime cap |
| `AP_PROJECT_EXECUTION_CONCURRENCY_LIMIT` | `5` (when the limiter is enabled) | Per-project concurrent-execution cap; over-limit requests get `429` |

The per-operation 60-second timeout is fixed in code. See [Latency](../architecture/latency) for how the budgets compose.
