When infrastructure fails mid-execution, your **data** survives and your **in-flight executions do not**. This codebase runs every execution synchronously, in-process, in the app container — there is no queue holding pending work and no replay mechanism to resume interrupted runs (see [Durable Execution](../architecture/durable-execution)). A crash interrupts the caller, and that is the whole story; this page documents exactly what that means.

<Note>
These guarantees describe the unified image in this repository. Older versions of this page promised queue-backed durability — requeued runs, replayed logs, drain-free rolling deploys — under a worker-fleet model that does not exist in this codebase ([Workers](../architecture/workers)).
</Note>

## What survives every crash

- **Your database.** Connections, tables, records, users, platform configuration, and scheduled-task definitions live in Postgres. Whatever finished before the crash is intact.
- **Your files.** Persisted files live in your configured file store (S3 or the database), committed before the crash.
- **Your schedules.** Scheduled-task definitions are re-registered from Postgres on boot, so a restarted replica picks them up again.

## What does not survive

- **In-flight executions.** The request the app was processing when it died is lost to its caller — the client sees a connection error and must retry. The platform does not re-run it anywhere.
- **Nothing is held in Redis for later.** Redis holds locks, rate-limit counters, and concurrency slots — none of which is user work. There is no queue whose durability you need to worry about.

## Roll replicas with in-flight requests in mind

Because there is no requeue-and-replay safety net, a rolling deploy or eviction is caller-visible for whatever it interrupts:

- The app handles `SIGTERM`/`SIGINT` by closing the HTTP server and letting in-flight requests settle before exiting. Requests that finish inside your orchestrator's termination grace period succeed.
- Anything slower than the grace period fails to its caller. Set the grace period with the execution timeout in mind ([Latency](../architecture/latency)), or take replicas out of rotation and let traffic drain to their siblings first.

## At-most-once, retried by the caller

The platform runs each accepted operation **at most once**: it either returns a result or dies with the process. There is no at-least-once redelivery, so nothing is automatically duplicated — but a **caller's retry** can repeat an operation whose side effects already happened. For operations with external side effects (sending a message, charging a card), make them idempotent at the piece or design the retry to tolerate a possible repeat.

## Governing configuration

There is no flag that buys crash recovery here. What you own is the durability of the backing stores — managed Postgres and your file store — and the retry behavior of the clients you build on the headless API.
