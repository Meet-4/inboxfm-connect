This is the production setup we recommend. It is sized from a single number — your **peak concurrent flows** — and everything else follows from there.

## What it looks like

One app tier that both serves the API and executes flows, plus managed Postgres, Redis, and S3 behind it — all in the **same region**.

In this build, executions run **in-process in the app container**: every project-attributable run passes through a fixed-size, platform-wide sandbox pool (10 slots per app replica). There is no Redis job queue and no separate execution tier. (The stock `docker-compose.yml` also starts `worker` replicas, but in this build those containers register only health endpoints — nothing executes there. Don't provision around them.)

| Component | Size each | How many |
|---|---|---|
| **App** | 2 vCPU / 4 GB | one per 10 concurrent flows |
| **Postgres** | 2 vCPU / 4 GB, managed | one, grows with the fleet |
| **Redis** | 1 vCPU / 1 GB, managed | one |
| **Object storage (S3)** | same region, signed URLs on | recommended for scale |

S3 is strongly recommended for production but not required: `AP_FILE_STORAGE_LOCATION` defaults to `DB`, and switching to S3 keeps flow bundles and piece archives out of the app tier and the database (walkthrough: [S3 Storage](./setup-s3)). At scale, co-locating S3 in-region keeps bundle fetch times low.

<Note>
As the app tier grows, budget its Postgres connections too — each app replica opens its own pool,
and Postgres's `max_connections` is shared across the whole fleet. See
[Postgres Connection Budget](./postgres-connection-budget).
</Note>

## Recommended config

Copy this:

```bash
AP_EXECUTION_MODE=SANDBOX_CODE_ONLY
AP_FILE_STORAGE_LOCATION=S3
AP_S3_USE_SIGNED_URLS=true
```

`AP_EXECUTION_MODE` defaults to `UNSANDBOXED`; `SANDBOX_CODE_ONLY` isolates flow-step code execution (accepted values are `SANDBOX_CODE_ONLY`, `SANDBOX_PROCESS`, `SANDBOX_CODE_AND_PROCESS`, and `UNSANDBOXED`).

<Warning>
Do **not** copy older guides that set `AP_WORKER_CONCURRENCY`, `AP_REUSE_SANDBOX`,
`AP_WORKER_GROUP_ID`, or `AP_PROJECT_WORKER` — none of those variables is read
by this build, and setting them silently does nothing. `AP_PRE_WARM_CACHE` is
likewise dead ([0.86.0](/install/reference/breaking-changes#0-86-0)). See
[Worker Groups](./worker-groups) for what replaced the per-worker knobs.
</Warning>

## Sizing

A run occupies one of the app replica's sandbox-pool slots for its **whole duration** (up to the flow-run timeout), so size by **concurrent flows**, not trigger rate:

```
app slots = app replicas × 10
app replicas = ceil(peak concurrent flows / 10)
```

At 50 concurrent flows: **5 app replicas** (10 vCPU / 20 GB total). Extra traffic beyond the pool waits — requests queue in-process and drain as slots free, and each project can be individually capped (see below).

To keep one noisy project from occupying the whole pool, enable per-project concurrency caps:

```bash
AP_PROJECT_EXECUTION_CONCURRENCY_LIMITER_ENABLED=true
AP_PROJECT_EXECUTION_CONCURRENCY_LIMIT=5
```

Details and defaults: [Worker Groups → per-project concurrency limits](./worker-groups).

## Limits

| Limit | Default | Env var |
|---|---|---|
| Flow run timeout | 600 s | `AP_FLOW_TIMEOUT_SECONDS` |
| Sync webhook response | 30 s | `AP_WEBHOOK_TIMEOUT_SECONDS` |
| Max webhook payload | 25 MB | `AP_MAX_WEBHOOK_PAYLOAD_SIZE_MB` |
| Step file size | 25 MB | `AP_MAX_FILE_SIZE_MB` |
| Flow run log size | 50 MB | `AP_MAX_FLOW_RUN_LOG_SIZE_MB` |

The complete table lives in [Limits](/install/reference/limits).

<Note>
Need per-project isolation or caps? See [Worker Groups](./worker-groups) —
dedicated worker groups are not implemented in this build; per-project
concurrency limits are.
</Note>
