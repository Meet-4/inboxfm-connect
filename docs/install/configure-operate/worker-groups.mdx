> **Status: not implemented in this build.** The dedicated worker-group feature
> described in older release notes (per-group queues, group-scoped workers, a
> Workers page in the console) does not exist in this codebase. The
> environment variables below are **not read by any code** — setting them does
> nothing. This page documents what is actually available instead.

## What does not exist

- **`AP_WORKER_GROUP_ID`** and **`AP_PROJECT_WORKER`** are never read. No code
  joins a worker to a group, and nothing scopes a worker to a project or a
  platform.
- There is **no per-group queue routing**. Executions are not dispatched
  through job queues at all — trigger and flow runs execute in-process in the
  app container (see [Production Setup](/install/configure-operate/production-setup)).
- There is **no Workers page** in the console (`/platform/infrastructure/workers`
  does not exist).
- The projects API still accepts a `workerGroupId` field and stores it, and the
  platform plan stores one too — but nothing reads those columns back. They are
  inert data; assigning a group has no effect.

## What you can use instead: per-project concurrency limits

The guard that exists today bounds **how many runs a single project can keep
in flight at once**, enforced at the single chokepoint every
project-attributable execution passes through (a fixed-size, platform-wide
in-process sandbox pool — 10 slots per app replica).

| Variable | Description | Default |
|---|---|---|
| `AP_PROJECT_EXECUTION_CONCURRENCY_LIMITER_ENABLED` | Enable the flat per-project in-flight execution cap. | `false` |
| `AP_PROJECT_EXECUTION_CONCURRENCY_LIMIT` | Concurrent in-flight executions allowed per project when the limiter is on. | `5` |
| `AP_PROJECT_EXECUTION_CONCURRENCY_SLOT_TTL_SECONDS` | Backstop TTL for a project's slots; refreshed on every acquire, so it only matters if a process dies mid-execution. | `900` |

On the **Enterprise and Cloud editions**, an admin can additionally assign a
project to a **concurrency pool** (`concurrency_pool.maxConcurrentJobs`), which
takes precedence over the flat limit for that project. See
[Manage Concurrency](/admin-guide/guides/manage-concurrency).

## Floor vs. ceiling

- A per-project execution **limit** is a **ceiling**: the most a project may
  run at once.
- This build has no **floor** mechanism — no capacity is reserved for a
  project. Capacity is shared best-effort across all projects hitting the same
  app instance; keep a project's limit low enough that a single project cannot
  occupy the whole in-process pool if isolation matters to you.
