Execution in this codebase is **synchronous and in-process**: every operation — `POST /v1/execute`, MCP tool calls, piece property loading, auth refresh, trigger hooks — runs inside the app container, against a fixed pool of sandboxed engine processes. There is no execution queue and no worker tier to scale ([Workers](/install/architecture/workers), [Separate Workers](/install/configure-operate/separate-workers)).

That changes what autoscaling means here. You scale **app replicas** (`AP_CONTAINER_TYPE=APP`, or the default `WORKER_AND_APP`), and capacity is simply "more replicas serving synchronous HTTP".

<Note>
**Scope:** the unified image in this repository. Scaling replicas of `AP_CONTAINER_TYPE=WORKER` adds no capacity — a `WORKER` container registers only the health routes; every execution-bearing module is gated on the app role.
</Note>

## The unit of capacity: one app replica

Each app replica owns its own, in-process:

- **Sandbox pool for interactive operations** — a fixed pool of ten sandbox "boxes" (`user-interaction-watcher.ts` routes property loads, auth validation, trigger hooks, and piece metadata round-robin across them; each box runs one operation at a time).
- **Sandbox for tool executions** — `POST /v1/execute` and the MCP `ap_run_action` tool run against a single-box runtime (`packages/runtime`), one tool execution at a time per replica.

The pool sizes are fixed in code — they are not tunable knobs. A replica's ceiling is its pools plus its CPU, and past that ceiling requests are **rejected, not queued** (see below).

## How fast capacity arrives

A new replica is useful as soon as it is serving HTTP. What happens on the way:

1. **Pod scheduling + image pull** — the orchestrator starts the container; this dominates cold-start scenarios and is ordinary Kubernetes/Docker behavior, not application behavior.
2. **Process boot** — the API registers its routes and connects to Postgres/Redis.
3. **Lazy sandbox builds** — nothing pre-builds. The first execution on a replica provisions its pieces into the local on-disk cache and forks the engine; later executions reuse both while the sandbox stays warm.

We do not publish numbers for these phases: prior figures on this page were measured against the retired queue-and-worker-fleet model and say nothing about this architecture. For current measurement methodology, see [Benchmark](/install/architecture/benchmark).

## Scaling down is graceful — but nothing holds your work

On `SIGTERM`/`SIGINT` the app stops accepting new requests and closes the HTTP server, letting in-flight requests finish, then exits. Because execution is synchronous and there is no queue:

- Requests that complete before the process exits succeed.
- Any execution still running when the process exits is **lost to its caller** — the client sees a connection error and is expected to retry.

There is no drain window to respect beyond your orchestrator's termination grace period: give slow executions enough grace to finish, or front them with a retrying client. Kubernetes' default 30 s period is shorter than the maximum time an execution may legally take (see [Latency](/install/architecture/latency) for the timeout budget).

## Saturation is signaled with 429s, not backlog

When a replica's pools are busy or a project is over its cap, the platform does not stash work for later. Two admission controls reject immediately:

- **Per-project execution concurrency limit** — an atomic Redis-backed counter admits up to `AP_PROJECT_EXECUTION_CONCURRENCY_LIMIT` (default 5) concurrent executions per project when the limiter is enabled; over-limit requests get `HTTP 429` with a `Retry-After` header. See [Manage Concurrency](/admin-guide/guides/manage-concurrency).
- **Sync-tier rate limit** — `POST /v1/execute` is rate-limited per project (`AP_API_RATE_LIMIT_SYNC_MAX`, default 60 per `AP_API_RATE_LIMIT_SYNC_WINDOW`, default 1 minute; disable with `AP_API_RATE_LIMIT_SYNC_ENABLED=false`).

Scale on what these produce: replica CPU, request rate, and the 429 rate. There is no queue depth to alert on, because there is no queue.

## Scheduled work survives restarts, runs in-process

Scheduled tasks are rows in Postgres fired by an in-process cron scheduler. On boot, each app replica re-registers the enabled schedules from the database, so scaling up does not duplicate them and restarts do not lose them. They are not queued work: a schedule fires as an in-process operation, and a fire time that passes with no replica running is **skipped, not caught up** — registration always computes the next occurrence from the present, so the schedule resumes with the next occurrence after boot.

## What to autoscale — and when not to

- **Tool executions (`POST /v1/execute`, MCP):** these are synchronous request/response calls. Autoscaling app replicas helps a growing *rate*; it cannot help a single slow execution. Size replicas for sustained rate, and set per-project concurrency caps to keep one project from consuming every box.
- **Bursty clients:** because over-capacity requests are rejected with `Retry-After`, clients must retry — an autoscaler reacting to 429s only helps if the load persists. For spiky synchronous load, prefer client-side rate shaping over elastic capacity.
- **Scale-down risk is caller-visible:** taking replicas away during load turns in-flight executions into client errors. Scale down when traffic is low, not merely when average CPU is low.
