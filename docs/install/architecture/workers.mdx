In this codebase, **no container named "worker" executes anything.** Every execution — `POST /v1/execute`, MCP tool calls, piece property loading, auth validation and refresh, trigger hooks, piece metadata extraction — runs **synchronously, in-process, inside the app container**, against a fixed pool of sandboxed engine processes. There is no job queue to pull from and no dispatch to another tier.

The `WORKER` **container role** still exists in the unified image (`AP_CONTAINER_TYPE=WORKER`, the same image as the app), so this page documents what it actually does — and what it no longer does.

## What a WORKER container actually does

Almost nothing, and that is by construction:

- `server.ts` gates every module on `system.isApp()`; a `WORKER` container registers **only the health routes** (`/api/v1/health`). It serves no API, no console, no MCP, no execution path.
- `system.isWorker()` exists only to flip the in-process health flag the health endpoint reports.
- It does not consume a Postgres connection-pool slot for its modules (see the [Postgres connection budget](../configure-operate/postgres-connection-budget)).

Scaling `AP_CONTAINER_TYPE=WORKER` replicas therefore adds no execution capacity. Run and scale the default `WORKER_AND_APP` (or `APP`) container instead. For the full breakdown, see [Separate Workers](../configure-operate/separate-workers).

## How execution actually scales

Because execution lives in the app process, the scaling and capacity questions are the app's:

- Each app replica owns its own fixed pools: a ten-box sandbox pool for interactive operations, and a single-box runtime for `POST /v1/execute` and MCP tool calls. The pool sizes are constants in code, not configuration.
- Throughput grows by adding **app replicas**; there is no fleet to rebalance and no queue to drain.
- Over-capacity requests are rejected with `HTTP 429` + `Retry-After` (per-project execution concurrency caps, and the sync-tier rate limit), never queued.

See [Autoscaling](./autoscaling) for the capacity and shutdown semantics, and [Latency](./latency) for what a single caller waits on.

## Failure behaviour

There is no queue to requeue work and no second tier to hand it to:

- A request that completes, completes; a request in flight when the process dies is **lost to its caller**, which sees a connection error and is expected to retry.
- On `SIGTERM`/`SIGINT` the app closes its HTTP server and lets in-flight requests settle before exiting — but there is no drain protocol and nothing survives the process.
- Durable state is your database: connections, tables, records, and scheduled-task definitions persist in Postgres regardless of app crashes. See [Crash Recovery](../guarantees/crash-recovery) for the honest guarantees.

## Sandbox & Network Isolation

How the code the engine runs is isolated is two independent choices:

- [**Sandboxing**](./sandboxing): `AP_EXECUTION_MODE` decides how user code is isolated from the host kernel. This is the most important security decision for multi-tenant deployments.
- [**Network Security**](./network-security): `AP_NETWORK_MODE` decides what the sandboxed code is allowed to reach on the network.
