Older versions of this page described a run-log replay system: every flow run checkpointed to a compressed log, a worker that died mid-run having its job re-queued and replayed by a fresh worker, steps skipped up to the interruption point. **None of that machinery exists in this codebase.** There is no run-log checkpoint loop, no queue to reassign interrupted work to, and no flow-run execution at all — the `flow` and `flow_run` tables were removed from the schema (the migration that drops them notes workflows are dropped permanently), and the engine's operation set contains no flow execution.

What this page documents instead is the honest contract: what an interrupted execution does, and what state actually survives a restart.

## What happens to an in-flight execution

Executions here are **single, synchronous operations** — `POST /v1/execute`, an MCP tool call, a piece property load, an auth refresh, a trigger hook. The caller's HTTP request holds the execution in the app's process:

- If the app process exits mid-execution (crash, OOM kill, deployment), the execution is **interrupted and lost to its caller** — the client sees a connection error. It is not re-run anywhere.
- Recovery belongs to the caller: the SDK, MCP client, or integration retries the request. Because an operation that never returned may have partially executed, treat any retried operation as a potential repeat and make its side effects idempotent where that matters.
- A slow operation that exceeds its sandbox timeout fails with a timeout error to the caller — same rule: the caller decides whether to retry.

## What actually persists

The data plane is durable because it lives in your database, not in the execution path:

- **Postgres** — connections, tables, records, scheduled-task definitions, users, platform configuration. All of it survives every restart, crash, and redeploy.
- **Object storage / DB-backed file store** — files created before an interruption are already persisted; nothing about an interrupted execution is.
- **Scheduled tasks** — their definitions are rows in Postgres, re-registered by each app replica on boot, so a restart does not lose them (see [Workers](../architecture/workers)).

## What this means operationally

- There is **no replay guarantee to rely on**: an operation is either completed (its result was returned and its side effects persisted) or failed. There is no "resumes from its last checkpoint".
- **Rolling deploys still work** — a replica terminating at grace lets in-flight requests finish; anything slower than the grace period fails to its caller. See [Autoscaling](../architecture/autoscaling).
- **Idempotency is the durability tool**: for operations with external side effects (sending a message, charging a card), design them to tolerate a client retry, because the platform will not de-duplicate a re-sent request.
