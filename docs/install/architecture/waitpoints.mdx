Older versions of this page documented a waitpoint system: a durable row representing a paused step on a flow run, `DELAY` and `WEBHOOK` resume types, resume endpoints under `/v1/flow-runs/:id/waitpoints/…`, and a job queue that carried the resume back to a worker. **None of it exists in this codebase:**

- The `waitpoint` table was **removed from the database schema** (dropped alongside `flow` and `flow_run`; the migration notes workflows are dropped permanently), and the API exposes **no waitpoint or flow-run routes** — `POST /v1/waitpoints` returns 404.
- There is no queue to carry a resume, and no worker to receive it ([Workers](./workers)).
- What survives in the engine is inert: a vestigial client that would call the now-nonexistent waitpoint endpoint, and a piece-context `ctx.run.createWaitpoint` stubbed to return a dummy no-op. A piece that tries to pause this way does not pause anything.

## What a piece author should do instead

Nothing in this codebase pauses execution across requests. The execution surfaces are synchronous, single operations ([Latency](./latency)):

- **For delayed work** — call the platform from your own scheduler, or use scheduled tasks, whose definitions persist in Postgres and re-register on boot.
- **For respond-then-callback patterns** — return from the operation immediately and have the external party invoke a follow-up operation with `POST /v1/execute` when the real answer arrives.
- **For long waits inside one operation** — there is no way to park it: operations are bounded by the sandbox timeout (60 s per operation; see [Latency](./latency)). Split the work at the caller.
