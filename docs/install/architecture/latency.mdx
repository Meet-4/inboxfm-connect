The headless API has no synchronous-webhook flow execution. Its synchronous surfaces are single **operations**: `POST /v1/execute` (run one piece action), MCP tool calls, and the interactive operations behind the console and MCP (piece property loading, auth validation, trigger hooks). The caller waits for the orchestration around the operation plus the operation's own work.

<Note>
**Scope:** every execution runs **in-process in the app container** against a fixed pool of sandboxed engine processes — there is no queue wait and no dispatch hop. Sandbox behavior depends on `AP_EXECUTION_MODE` (`UNSANDBOXED` by default; see [Sandboxing](/install/architecture/sandboxing)).
</Note>

## What shapes the wait

| Situation | Caller waits for |
|---|---|
| **Warm** — the operation's sandbox is already up and the pieces are cached | Provision + boot are near-zero; the operation's own work dominates |
| **Cold** — first use of a sandbox on a replica, or a non-reusable execution mode | Provisioning pieces into the local cache, then forking and booting the engine |
| **Timeout** — the operation never returns in time | The operation is failed with a timeout error; see the budget below |

## Warm vs cold

A sandbox is an engine child process forked by the app. Whether it is reused across operations is decided by `AP_EXECUTION_MODE` — there is no separate reuse knob:

- `UNSANDBOXED` (the default) and `SANDBOX_CODE_ONLY` are trusted reuse modes: a sandbox that finished cleanly is kept warm and the **next operation on the same box reuses the booted engine process**.
- `SANDBOX_PROCESS` and `SANDBOX_CODE_AND_PROCESS` are cold by design: every operation gets a fresh isolation box.

You hit cold when:

- It is the first execution after a deploy, restart, or scale-up (boxes build lazily on first use).
- The pieces involved are not yet in the replica's local on-disk cache — provisioning installs them once, then the cache serves later executions.
- The execution mode is a process-isolation mode, where cold is the guarantee you asked for.
- A previous operation on the same box failed — a failed box is torn down and rebuilt rather than reused.

A cold path pays provisioning (piece install, cache write) plus boot (fork the engine, engine startup, socket handshake) before the operation itself runs. We do not publish millisecond figures on this page: the numbers that were here were measured against the retired worker-fleet model. Current measurements belong to the [benchmark gate](/install/architecture/benchmark), which runs against the live headless API.

## Where the time goes

Every execution passes through three phases, in order:

| Phase | What it covers | Warm | Cold |
|---|---|---|---|
| **Provision** | Installing the operation's pieces and code artifacts into the local on-disk cache. | cache hits | real work |
| **Boot** | Forking the engine child process, Node startup, and the socket handshake. | skipped (reused) | real work |
| **Run** | The engine executing the operation — the piece's own code and any third-party calls it makes. | always | always |

The runtime records these three durations per execution (`provisionMs`, `bootMs`, `runMs`) as structured observability events, so a deployment can attribute its own latency from its own logs. There is no in-app popover UI for this breakdown.

Your own work usually dominates the **Run** phase: a piece action that calls a third-party API waits on that API. Next to a real outbound call, the platform's provision/boot overhead is the smaller number — and on a warm box it is near zero.

## The timeout budget

Each operation is capped at **60 seconds** (a code constant on both execution paths), enforced inside the sandbox: an operation that exceeds it fails with a sandbox timeout error rather than hanging the caller. The engine child process itself is additionally bounded by `AP_FLOW_TIMEOUT_SECONDS` (default 600 s) and by the sandbox memory limit `AP_SANDBOX_MEMORY_LIMIT` (KB; default 1048576 = 1 GB) — see [Reserved Resources](/install/guarantees/reserved-resources).

## Admission control: expect 429s, not waits

When a project exceeds its execution concurrency cap, or the sync tier's rate limit (`AP_API_RATE_LIMIT_SYNC_MAX`, default 60/min) is hit, the request is rejected with `HTTP 429` and a `Retry-After` header — it is **not** held in a queue. A latency-sensitive client should treat 429 as the platform's honest "busy now" signal. See [Manage Concurrency](/admin-guide/guides/manage-concurrency) and [Autoscaling](/install/architecture/autoscaling).

## Reduce it

- **Stay in a reuse mode:** the default `AP_EXECUTION_MODE=UNSANDBOXED` (or `SANDBOX_CODE_ONLY` for multi-tenant isolation) keeps boxes warm. Process-isolation modes are cold by design.
- **Scale replicas, not hopes:** each app replica brings its own fixed pools. More replicas raise concurrent capacity; they do not speed up any single execution. See [Autoscaling](/install/architecture/autoscaling).
- **Cache-friendly pieces:** the first execution of a piece pays its install; steady-state traffic does not.
- **Don't hold a synchronous call against a slow third party:** if the piece's work can be slow, invoke it from a caller that can retry on the 60 s cap rather than a request path that cannot.
