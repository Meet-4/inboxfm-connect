This page describes the benchmarking harness in `benchmark/` and what it measures against this codebase. The numbers that previously lived here (throughput of a 40–160 worker fleet at a 1:10 app-to-worker ratio) were measured against the retired queue-and-worker-fleet execution model, which does not exist in this tree: execution is synchronous and in-process in the app container, there is no job queue, and a `WORKER` container registers only health routes. Those results are preserved as a historical experiment record in `benchmark/EXPERIMENTS.md`; they are not reproduced here because they say nothing about the current architecture.

For current numbers, run the measurement yourself with the harness below — we deliberately do not publish figures we have not measured against this model.

## What executes under load

<Steps>
  <Step title="A piece action via POST /v1/execute">
    The gate's `execute-text-helper` scenario runs `@inboxfm-connect/piece-text-helper` `concat` through the synchronous execute endpoint, asserting the output.
  </Step>
  <Step title="An auth + database read path">
    The `connections-list` scenario exercises `GET /v1/connections` — request authentication plus a database read — to track the control plane separately from execution.
  </Step>
</Steps>

The compute is trivial by design: what the benchmark measures is the orchestration around the operation — admission control, provisioning from the piece cache, sandbox reuse, and the engine round-trip — which is what actually shapes production latency.

## The shape under test

- **Execution is in-process in the app tier.** `POST /v1/execute` runs in the app container against a single-box sandbox runtime; the interactive operations run against a fixed ten-box pool per replica. There is no queue and no execution in any other container.
- **Throughput scales with app replicas** (`APP_REPLICAS`), each bringing its own pools. `WORKER` replicas add no execution capacity (see [Workers](/install/architecture/workers)).
- **Admission control is visible in the results:** per-project concurrency limits and the sync-tier rate limit reject over-capacity requests with `429` + `Retry-After` instead of queueing them, so load profiles must stay under those caps or the gate measures rejections, not service time.
- **Warm vs cold is decided by `AP_EXECUTION_MODE`:** trusted modes (`UNSANDBOXED`, `SANDBOX_CODE_ONLY`) reuse booted engine processes across executions; process-isolation modes are cold by design. See [Latency](/install/architecture/latency).

## The harness

`benchmark/gate` is a repeatable gate that compares a run against a committed, reviewed baseline (`benchmark/baselines/`) and fails when latency, throughput, or the error rate regresses beyond a noise-aware threshold. It is plain Node with no dependencies:

- **selftest** — runs on every PR touching `benchmark/gate/**` against an in-process stub server.
- **nightly** — runs against a configured deployment; skips safely when the target isn't configured.
- **full fleet** — manual, opt-in: GKE via `benchmark/run-gke.sh`.

```bash
node benchmark/gate/cli.mjs selftest
node benchmark/gate/cli.mjs run --scenario execute-text-helper --tier nightly --out results.json
node benchmark/gate/cli.mjs compare --baseline benchmark/baselines/execute-text-helper.nightly.json --results results.json --summary summary.md
```

See `benchmark/gate/README.md` for the scenarios, required environment variables (`BENCH_BASE_URL`, `BENCH_API_KEY`, `BENCH_PROJECT_ID`, `BENCH_CONNECTION_ID`), and the results format.

## Reproducing at cluster scale

```bash
benchmark/run-gke.sh [requests_per_round] [concurrency] [rounds]
```

The script deploys `benchmark/k8s-sandbox.yaml` (app replicas, Postgres, Redis), provisions a Text Helper connection and API key, and drives `POST /v1/execute` through the app load balancer with the load runner in `benchmark/gate`. It reports cold-boot latency, warm latency and throughput, and per-pod CPU. `/v1/execute` runs in the app tier, so scale with `APP_REPLICAS`. The manifest still carries a vestigial `worker` Deployment (including `AP_WORKER_CONCURRENCY` and `AP_REUSE_SANDBOX` env entries that no current code reads); with current code those pods register only health routes and execute nothing.

<Tip>
The GKE rig runs in `SANDBOX_CODE_ONLY` mode (V8 isolation), a trusted reuse mode — booted engine processes are kept warm across executions. It does **not** represent the performance of process-isolation modes, which are cold by design, and it does **not** represent the performance of Inboxfm Connect Cloud, which uses a different sandboxing mechanism for multi-tenancy. See [Sandboxing](/install/architecture/sandboxing).
</Tip>
